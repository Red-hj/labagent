| 检查项 | 复现方法 | 结果与证据 |

| 首轮诊断 | 上传 `fault/` 中的拓扑与四份日志，提出 PC1 无法访问 PC2 的问题。核对目标观测并要求补交修正后的设备输出。 | 首轮需要补证，故障阶段双向均 1 发 0 收。 [材料入口](evidence/01-materials.png) |
| 地图与路径 | 切换「拓扑地图」，从 PC1 检查到 `192.168.20.10` 的路径，再以修复材料重复。 | 图包含 PC1、R1、R2、PC2。路径从失败转为通过。 [故障路径](evidence/02-map.png) |
| 协作与同名更新 | 由成员甲同步初始材料并分配检查，由成员乙提交四份同名修复日志、完成检查，再在共享会话提交复测。 | 共享材料为五份原始材料和一份验证要求，四份日志更新，任务完成。 [协作](evidence/10-team-result.png) · [复测证据](evidence/04-复测证据.json) |
| 复测和引用 | 检查双向 Ping 与双方的 OSPF 路由来源，按文件名及行号对照修复日志。 | 4 项全部通过。逐条校对引用与修复材料完全一致，网页可跳到 `R1-run.log` 第 8 行。 [引用高亮](evidence/08-citation.png) |
| 恢复与报告 | 再读取共享会话，打开历史并获取报告。 | 同一个会话保留两轮，最终结论为「提交的测试输出核验通过」，报告列出复测证据。 [恢复界面](evidence/05-session-report.png) · [实验报告](evidence/实验报告示例.md) |
| 截图与上传 | 使用仓库的模拟终端截图检查 OCR，定位第 6 行。用空文件检查错误响应。 | 正常截图提取 6 行，引用高亮对应坐标。空文件得到 HTTP 400。 [截图引用](evidence/11-screenshot-citation.png) |
| 失败与重试 | 在浏览器模拟首个流式诊断请求返回 HTTP 503，点击「重新发送」。 | 重试前保留问题和 5 份材料，重试后收到本地可控模型结果。聊天与任务控制回归还覆盖追问草稿和断线恢复。 [失败](evidence/12-draft-retry.png) · [重试](evidence/13-retry-result.png) |
| 手机尺寸 | 将 Edge 内容区设为 390 × 844，展开 `topology.txt` 并滚动到恢复后对话的第二轮。 | 页面宽度 384px，无整页横向滚动，可读到复测结论。 [窄屏材料](evidence/04-mobile.png) · [窄屏对话](evidence/09-mobile-conversation.png) |
| 长对话阅读 | 用本地可控模型建立七轮会话，刷新后在 390px 页面分别滚到第一轮和最后一轮。 | 七轮均恢复，首尾回复可读。 [第一轮](evidence/14-mobile-history-first.png) · [最后一轮](evidence/15-mobile-history-last.png) |
