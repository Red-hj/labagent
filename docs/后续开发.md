### 功能深度与下一步

当前核心是“实验目标→主动选检查→获取新观测→核对修改结果”的持续排查流程。跨轮实验摘要和任务停止/恢复已接入；本轮完善按候选原因区分能力和采集成本选择下一项检查，并复用已提交观测。下一步优先真实 eNSP 案例联调，将修改前后观测、目标完成情况与建议关联起来；创新效果通过真实案例的操作数量、判断依据与复测结果体现。

### 实施边界与具体落点

- 执行层负责模型调用、工具循环、每轮状态和检查点；实验层继续负责原文引用、设备观测、实验目标、提示级别、报告与账号范围。React 负责展示和交互，不在浏览器内决定实验是否达标。
- 第一阶段建议从现有 `session_id → attempt → tool_call_id` 对应关系开始，不再建立另一套业务历史或日志库。进度流可继续使用 NDJSON；新的事件增加稳定标识与结构化状态，不需要为参考 Codex 而改用 JSON-RPC 或 WebSocket。
- 当前网站通过 AgentArts 执行诊断，浏览器手动采集实验电脑输出后再交给诊断。让云端模型主动调用学生电脑工具，需要网站转发、当前账号绑定和云端工具回传的明确通道；仅迁移 React 或让云端访问 `localhost` 无法打通这段链路。
- 同一轮工具可以有执行成功、执行失败和结果未送达等情况；实验目标的 `passed/failed/needs_evidence` 单独保留。一次工具成功只表示得到输出，不表示实验完成。
- React 迁移前向共同页面维护者说明入口、组件范围及兼容期；事件、任务取消及工具回传变更前说明接口范围。先以分支 PR 验证，沿用现有部署与账号数据。
- 多智能体留待出现可独立评测的子任务时再引入。当前先把单个智能体的证据、状态和恢复做好；直接接入 Codex / Claude Agent SDK 另做模型兼容、部署与费用评估，当前实现沿用已有模型与运行时。

### 独立配置的三组评测

沿用首轮清单和标签格式。另建一个本地输入目录，放入 `manifest.json` 及 `inputs/bNNN.json`。清单记录 `version`、`origin`、`device_verified`、`review_status` 和 `cases`，每项含 `id`、`file`、`sha256`。配置题沿用首轮的请求字段和故障码；标签文件使用同一版本及相同编号，按 `cases` 保存每例的预期诊断。独立清单可少于 60 例。

```powershell
python -X utf8 scripts/evaluate_b.py prepare-model --benchmark-dir runtime/independent-b/inputs-pack --mode model-direct --output runtime/independent-b/direct-requests.jsonl
python -X utf8 scripts/evaluate_b.py run-model --benchmark-dir runtime/independent-b/inputs-pack --mode model-knowledge --limit 7
python -X utf8 scripts/evaluate_b.py benchmark --benchmark-dir runtime/independent-b/inputs-pack --labels runtime/independent-b/labels.json --mode rules --output runtime/independent-b/rules
```

两组模型用同一输入目录、样本数和调用参数。先查看计划，获授权的模型已配置时，用对应模式加 `--execute --env-file .env --output …` 保存预测。评测模型组时沿用上述 `benchmark` 命令和标签，改为对应模型模式并传入 `--predictions`，最后用 `compare` 汇总。准备请求和调用模型时只读取输入；三组评分时检查输入清单与标签是否一致。

从项目的 `data/cases` 选取 7 例公开配置，含 3 例正常、3 例故障和 1 例不支持的配置。固定同一份输入和标签，统一要求核对互联配置和拓扑。纯模型和知识增强各用 DeepSeek Flash 调用 7 次，温度 0.1，每次最多 800 个输出 token。知识增强每例附 3 条检索片段，21/21 条均核对过原文行号和来源。

| 指标 | 规则 | 纯模型 | 知识增强 |
| --- | ---: | ---: | ---: |
| 状态吻合 | 7/7 | 4/7 | 4/7 |
| 严格匹配 | 7/7 | 2/7 | 1/7 |
| 故障严格定位 | 3/3 | 2/3 | 1/3 |
| 正常例误报 | 0/3 | 2/3 | 2/3 |
| 不支持配置待确认 | 1/1 | 0/1 | 0/1 |
| 格式无效／缺预测记录 | 0／0 | 1／0 | 1／0 |
| 模型请求数／输入输出 token | — | 7／5,533 | 7／10,252 |
| 模型单例耗时中位数 | — | 951 ms | 1,179 ms |

两组模型都把本地 OSPF 进程号不同和合法多区域配置误判为区域失配，并把不支持的配置判为故障。知识增强组漏报了多故障例的子网不匹配。这次仅依据配置快照评分，实际修复效果待设备复测。用原输入、标签和模型存档复跑 60 例，三组严格匹配仍为 60/60、30/60、33/60。

#### 逐链路配置证据复测

`prepare-model` 和 `run-model` 可加 `--parsed-links`，附上链路两端从配置解析出的本地进程号、OSPF 区域、IPv4 网段、显式管理状态和原文行号。解析范围外的 OSPF 行保留行号。`compare` 会核对两组模型的证据选项。

沿用上述 7 例、原提示词、原检索片段和 DeepSeek Flash 调用参数，只为知识增强请求追加链路证据。一次请求超时后，用相同内容重试一次，收齐 7 份预测。

| 指标 | 原知识增强 | 附链路证据 |
| --- | ---: | ---: |
| 状态吻合 | 4/7 | 5/7 |

### 2026-11-28 FRRouting 邻居 JSON 验收

开放排查可读取 `show ip ospf neighbor json` 的默认邻居表。按 Router ID 与 `nbrState` 核对目标，引用设备输出中对应的两行。完整绑定的 JSON 表可用于核对邻居缺失。新输出截断、字段冲突或指定了其他 VRF 时，按命令范围和已有证据继续核对。[FRRouting OSPF 命令](https://docs.frrouting.org/en/stable-10.2/ospfd.html#showing-information)

重放仓库 FRRouting R1 和 R2 的故障及恢复日志。恢复时两端邻居均达到 Full。以原始命令输出绑定并标注完整的空表时，两端目标均未满足。逐项核对了 Router ID、状态和空表的原文引用。

检查规划按设备复用已核实的默认邻居表，文本与 JSON 可用于同一项检查。若当前目标中的 Router ID 未出现，只有绑定并标注完整的表可以作为缺失依据。最新采集不全、状态冲突或配置已改变时，仍可安排复测。

配置变更后，从上一轮沿用的邻居日志保留为历史材料。工作台的目标核对、检查规划和报告都等待本次复测。后续只追问也会保留该状态。重新采集或提交绑定当前配置的邻居输出后可更新验收结果，哪怕新输出与改动前的原文相同。对话中粘贴的邻居输出也按配置变更时间判断。改动前的输出可回查，改动后新粘贴的输出可供后续追问使用。本轮绑定输出优先于先前粘贴的结果。

已经验收的会话收到新的邻居输出后，可以直接核对已保存的目标。新证据显示邻居缺失、状态不符或采集不完整时，会话重新等待该项复测。模型暂不可用时，报告仍记录本轮状态和原文。
