# OSPF 实验环境与复测

本项目没有安装或控制网络仿真软件。这里提供可供现有华为 VRP 实验环境使用的配置参考，设备型号、接口名称及导入方式须与实际环境对应。配置尚未在真实设备上验证。

## 实验拓扑

```text
PC1 ── R1 GE0/0/2    R1 GE0/0/0 ── R2 GE0/0/0    R2 GE0/0/2 ── PC2
```

| 节点或接口 | 地址 | 网关 |
| --- | --- | --- |
| PC1 | 192.168.10.10/24 | 192.168.10.1 |
| R1 GE0/0/2 | 192.168.10.1/24 | 无 |
| R1 GE0/0/0 | 10.12.0.1/24 | 无 |
| R2 GE0/0/0 | 10.12.0.2/24 | 无 |
| R2 GE0/0/2 | 192.168.20.1/24 | 无 |
| PC2 | 192.168.20.10/24 | 192.168.20.1 |

正常配置位于 `data/lab/R1_correct.cfg` 和 `R2_correct.cfg`。故障参考是 `R2_area_fault.cfg`，其中 R2 被配置到 Area 1，实验要求 Area 0。配置应在已有的可控实验环境中使用。

区域不匹配时，直连接口间仍可能正常 Ping。演示应检查 OSPF 邻居、远端路由和 PC1 到 PC2 的通信，而不能声称直连接口 Ping 必然失败。

## 采集运行结果

在配置修改生效并等待协议收敛后，按实际设备命令采集：

```text
display ospf peer
display ip routing-table
```

在 PC1 上 Ping 192.168.20.10。记录收发包数量。在 `/workbench` 可提交支持的邻居、路由和 Ping 原始输出，或者填写下面的结构化观测。此双端互联实验预期邻居为 Full，共享广播网的多设备场景需另行设计验证规则。

```json
{
  "neighbors": [{"link_id": "r1-r2", "state": "Full"}],
  "pings": [{
    "source": "PC1",
    "target": "192.168.20.10",
    "sent": 5,
    "received": 5
  }]
}
```

数据仅为格式示例，请填写真实结果。网页内勾选“针对当前配置新采集”，点击“绑定当前配置指纹”，再提交复测。

通过 API 复测时，先向 `/api/fingerprint` 发送当前诊断输入，取得 `config_fingerprint`，放入 `observations` 后提交诊断。指纹由配置、拓扑和实验要求共同生成；修改其中任何一项，旧观测就不能用于通过本次验证。

该机制不验证观测真实性。页面明确标记为用户提交的观测，不宣称本地程序执行了设备命令。

## B 组首批实验

五例共用上面的拓扑和地址表。`data/team_cases/lab_01` 是正确基线；`lab_02` 到 `lab_05` 分别覆盖 Area、接口关闭、OSPF 未启用、互联 IP 网段错误。

1. 从 `lab_01` 的配置快照建立正常基线。按设备型号确认接口名；在终端逐段进入接口与 OSPF 视图配置，`#` 是快照分隔符。检查预期 Full 邻居、双向 OSPF 路由与端点 Ping。
2. 每次从基线开始，按照该例 `notes.md` 注入一个故障。仅将 `input.json` 交给诊断器；`expected.json` 用来对照，`repaired.json` 用来确认修复后的静态检查。
3. 在 R1/R2 保存 `display ip interface brief`、`display ospf peer`、`display ip routing-table`，在 PC1 和 PC2 记录目标、收发数量及原始输出。修复后重新采集，保留设备型号、仿真版本、时间和对应配置。仓库中的 `before.txt` 和 `after.txt` 是记录模板；真实记录放本地 `runtime/`。
4. 若在 `/workbench` 复测，使用同一会话，将真实观测绑定到当前配置再提交。若使用首页，上传实际修复配置和端点的 Ping 原文，核对目标匹配并下载实验报告。

在项目根目录可直接运行：

```powershell
python -X utf8 app.py diagnose data/team_cases/lab_02/input.json
python -X utf8 app.py diagnose data/team_cases/lab_02/repaired.json
```

预期先看到 R2 互连接口的 Area 不符合要求，修正后进入 `awaiting_verification`；只有实际复测才能确认端到端恢复。

### 保存并核验原始输出

没有实验环境时，先运行离线案例和评测即可；以下步骤用于后续设备验收。初始化只创建空目录，不生成命令输出：

```powershell
python -X utf8 scripts/verify_b_evidence.py init lab_02 runtime/b-evidence/lab_02
python -X utf8 scripts/verify_b_evidence.py check runtime/b-evidence/lab_02
```

在 `before/` 和 `after/` 各保存以下 UTF-8 原文：

| 文件 | 实际采集内容 |
| --- | --- |
| `R1-config.txt`、`R2-config.txt` | 两台路由器各自的 `display current-configuration` |
| `R1-ospf.txt`、`R2-ospf.txt` | `display ospf peer` 详情；无邻居时保留设备明确显示的零邻居汇总 |
| `R1-routes.txt`、`R2-routes.txt` | 两份完整的 `display ip routing-table` |
| `PC1-ping.txt`、`PC2-ping.txt` | 分别 Ping `192.168.20.10`、`192.168.10.10` 的原始收发统计 |

在 `record.json` 填写 `source`（`vrp_device` 或 `vrp_simulator`）、`environment`（型号和版本），以及两个阶段的 `captured_at`（带时区，如 `2026-11-12T14:00:00+08:00`）。确实完整采集路由表后，再把各阶段的 `complete_route_tables` 设为 `true`。

重新运行 `check`。`verification.json` 给出缺失文件、配置匹配、邻居、两端远端 OSPF 路由及双向 Ping。`pending` 表示材料待补；`mismatch` 表示提交观测未符合本例预期；`recorded_observations_match` 表示记录与要求吻合。用测试夹具时必须选 `fixture`，结果仅为 `fixture_pass`。如设备输出格式不同，保留原文并记录差异，勿补写不存在的行。
