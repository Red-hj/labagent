# OSPF 实验环境与复测

本项目没有安装或控制网络仿真软件。这里提供可供现有华为 VRP 实验环境使用的配置参考，设备型号、接口名称及导入方式须与实际环境对应。配置尚未在真实设备上验证。

## 实验拓扑

```text
PC1 ── R1 GE0/0/2    R1 GE0/0/0 ── R2 GE0/0/0    R2 GE0/0/2 ── PC2
```

| 节点或接口 | 地址 | 网关 |
| --- | --- | --- |
| PC1 | 192.168.10.10/24 | 192.168.10.1 |
| R1 GE0/0/2 | 192.168.10.1/24 | 无 |
| R1 GE0/0/0 | 10.12.0.1/24 | 无 |
| R2 GE0/0/0 | 10.12.0.2/24 | 无 |
| R2 GE0/0/2 | 192.168.20.1/24 | 无 |
| PC2 | 192.168.20.10/24 | 192.168.20.1 |

正常配置位于 `data/lab/R1_correct.cfg` 和 `R2_correct.cfg`。故障参考是 `R2_area_fault.cfg`，其中 R2 被配置到 Area 1，实验要求 Area 0。配置应在已有的可控实验环境中使用。

区域不匹配时，直连接口间仍可能正常 Ping。演示应检查 OSPF 邻居、远端路由和 PC1 到 PC2 的通信，而不能声称直连接口 Ping 必然失败。

## 采集运行结果

在配置修改生效并等待协议收敛后，按实际设备命令采集：

```text
display ospf peer
display ip routing-table
```

在 PC1 上 Ping 192.168.20.10。记录收发包数量。在 `/workbench` 可提交支持的邻居、路由和 Ping 原始输出，或者填写下面的结构化观测。此双端互联实验预期邻居为 Full，共享广播网的多设备场景需另行设计验证规则。

```json
{
  "neighbors": [{"link_id": "r1-r2", "state": "Full"}],
  "pings": [{
    "source": "PC1",
    "target": "192.168.20.10",
    "sent": 5,
    "received": 5
  }]
}
```

数据仅为格式示例，请填写真实结果。网页内勾选“针对当前配置新采集”，点击“绑定当前配置指纹”，再提交复测。

通过 API 复测时，先向 `/api/fingerprint` 发送当前诊断输入，取得 `config_fingerprint`，放入 `observations` 后提交诊断。指纹由配置、拓扑和实验要求共同生成；修改其中任何一项，旧观测就不能用于通过本次验证。

该机制不验证观测真实性。页面明确标记为用户提交的观测，不宣称本地程序执行了设备命令。

## B 组首批实验

五例共用上面的拓扑和地址表。`data/team_cases/lab_01` 是正确基线；`lab_02` 到 `lab_05` 分别覆盖 Area、接口关闭、OSPF 未启用、互联 IP 网段错误。

1. 从 `lab_01` 的配置快照建立正常基线。按设备型号确认接口名；在终端逐段进入接口与 OSPF 视图配置，`#` 是快照分隔符。检查预期 Full 邻居、双向 OSPF 路由与端点 Ping。
2. 每次从基线开始，按照该例 `notes.md` 注入一个故障。仅将 `input.json` 交给诊断器；`expected.json` 用来对照，`repaired.json` 用来确认修复后的静态检查。
3. 在 R1/R2 保存 `display ip interface brief`、`display ospf peer`、`display ip routing-table`，在 PC1 和 PC2 记录目标、收发数量及原始输出。修复后重新采集，保留设备型号、仿真版本、时间和对应配置。仓库中的 `before.txt` 和 `after.txt` 是记录模板；真实记录放本地 `runtime/`。
4. 若在 `/workbench` 复测，使用同一会话，将真实观测绑定到当前配置再提交。若使用首页，上传实际修复配置和端点的 Ping 原文，核对目标匹配并下载实验报告。

在项目根目录可直接运行：

```powershell
python -X utf8 app.py diagnose data/team_cases/lab_02/input.json
python -X utf8 app.py diagnose data/team_cases/lab_02/repaired.json
```

预期先看到 R2 互连接口的 Area 不符合要求，修正后进入 `awaiting_verification`；只有实际复测才能确认端到端恢复。

### 在网络地图核对 B 组实测

在首页选“新的排查”，一起上传 `data/team_cases/lab_02/map_materials/fault/` 下的五个文件。材料来自同一次 FRRouting / WSL2 隔离实验。标题行用于绑定设备与命令，删去了宿主机标识和 IPv6 链路本地地址；IPv4 地址、路由、邻居与 Ping 统计来自采集输出。

| 阶段 | PC1 到 192.168.20.10 | PC2 到 192.168.10.10 | 对照证据 |
| --- | --- | --- | --- |
| `fault` | PC1 → R1，R1 无目标路由 | PC2 → R2，R2 无回程方向目标路由 | 两端无邻居，Ping 各 1 发 0 收 |
| `repaired` | PC1 → R1 → R2 → PC2 | PC2 → R2 → R1 → PC1 | 两端 Full，内核安装对端网段的 OSPF 路由，Ping 各 5 发 5 收 |

在“网络地图”选择源设备与对应目标，展开路由步骤可跳转原文。故障阶段 R2 的 `transit` 接口在 Area 1；恢复到 Area 0 后，从 `repaired/` 上传同名文件替换故障材料，再比较四台设备、三条连线与双向路径。地图从提交材料推导路径，端到端是否通过由实测 Ping 核对。

### 用 FRRouting 复现 Area 错误与接口关闭

工作台的“用示例体验一次完整排查”可选择 B 组的区域错误或接口关闭实测，查看故障、修复和逐项依据。接口关闭示例使用 R2 内核报告的接口管理状态，加上直连 Ping、双向端到端 Ping、两端 Full 邻居和两端远端 OSPF 路由，共八项检查。

在安装 FRRouting、iproute2、ping 和 Python 的 Linux 实验环境中，从项目根目录运行以下命令。WSL2 已在 Alpine 环境验证。

```sh
mkdir -p runtime
sudo sh scripts/run_b_frr_lab.sh lab_03 "$PWD/runtime/frr-lab03"
python3 scripts/export_b_frr_lab.py runtime/frr-lab03 runtime/frr-lab03/run.json
```

把第一条实验命令中的 `lab_03` 换成 `lab_02`，并给采集与导出指定另一个新目录，即可复测区域错误。脚本在隔离的 Linux 网络命名空间内建立两台路由器和两台主机，依次保存正常基线、故障与修复原文。`lab_03` 在 R2 执行 Linux 接口的管理关闭和恢复，OSPF 仍由 FRRouting 运行。导出核对原文并移除宿主机名、域名及链路地址字段。可把导出的 `run.json` 上传工作台查看运行对照。使用华为 VRP 采集时按下节操作。

### 实测分步修复与未达标结果

在 WSL2 的 FRRouting 10.2.2 实验中，给 R2 同时注入互联口管理关闭和 Area 1 区域错误。保留同轮正常基线、叠加故障、仅启用接口、再修正区域四次采集。

| 阶段 | 实际结果 | 目标通过 |
| --- | --- | ---: |
| 叠加故障 | R2 接口被管理关闭，直连及端到端 Ping 失败，两端缺 Full 邻居及远端 OSPF 路由 | 0/8 |
| 启用 R2 接口 | 接口管理状态恢复，R1 到 R2 直连 Ping 5 发 5 收，两端邻居和远端路由仍未恢复，双向端到端 Ping 仍失败 | 2/8 |
| 修正 R2 区域 | 两端邻居均为 Full，安装远端 OSPF 路由，两个方向的端到端 Ping 分别为 5 发 5 收 | 8/8 |

在首页上传 [分步实测记录](../data/examples/frr_lab02_partial.json)，询问三个阶段各自满足了哪些目标。完整修复方案包含启用接口和恢复 Area 0 两步。导出的实验报告保留各阶段的检查结果和 FRRouting 版本。复采命令如下。

```sh
mkdir -p runtime
sudo sh scripts/run_b_frr_lab.sh lab_02_partial "$PWD/runtime/frr-partial-raw"
python3 -B scripts/export_b_frr_lab.py runtime/frr-partial-raw runtime/frr-partial-run.json
```

导出器会按采集时间、配置、接口状态以及邻居、路由、Ping 原文重新核对结果。原始文件在 `runtime/frr-partial-raw/`。

在独立命名空间复采两次，均得到 0/8、2/8、8/8。用同一会话先提交部分记录再补齐完整记录。两轮 DeepSeek Flash 回复均未通过工具证据协议，工作台按已验算的运行记录分别输出未达标和全部达标结论，报告保留两个阶段的目标数与 FRRouting 版本。

### 实测 OSPF 失配与备用静态路由

在 FRRouting 10.2.2 中，两端预先配置管理距离 200 的静态路由。正常时选中 OSPF 路由。只改变 R2 互联口的区域后，两端都失去 Full 邻接，但改用备用静态路由，双向端点 Ping 仍各为 5 发 5 收。修正区域后，两端恢复 Full，选中的远端路由重新变为 OSPF。按双向端点 Ping、直连 Ping、双端路由来源和双端邻接共七项检查，故障阶段通过 3 项，修复阶段通过 7 项。[FRRouting 静态路由命令说明](https://docs.frrouting.org/en/latest/static.html)

在首页新建排查，上传 [实测记录](../data/examples/frr_lab02_backup.json)，询问“为什么故障阶段双向能 Ping，OSPF 实验却只有 3 项通过？”运行对照可查看所选路由来源、邻接与原始 Ping 统计。要自行复采，将上述实验命令的用例换成 `lab_02_backup`，采用新目录，确保 FRRouting 包含 `staticd` 与 `mgmtd`，再用同一导出脚本核对结果。

将新采材料与诊断建议对照：先用上面的导出脚本生成 `run.json`，再运行下方命令。故障阶段核对是否只改 R2 的 transit 区域并保留备用路由；修复阶段核对生效路由是否切回 OSPF、Ping 是否通过。采集和模型输出均保存在 `runtime/`。

```powershell
python -X utf8 scripts/evaluate_diagnostic_workflow.py --execute --env-file .env --frr-capture runtime/frr-backup/run.json --mode goals --case frr-static-fallback --case frr-healthy-with-backup --output runtime/frr-backup-advice
```

使用 v0.20.1 的 MCP 采集入口时，远端输出即使省略终端提示符，也可根据材料开头的设备和命令识别路由表与 Ping。正文若有明确的终端提示符，以正文的设备为准，原文行号按上传材料计数。本地通过真实 stdio MCP 进程与出站桥接处理器回放了既有 FRRouting 采集：R1 选择 OSPF 路由、下一跳为 10.12.0.2，引用准确落在材料第 5 行；同一输出不会当作 R2 的证据。

将故障与修复阶段的双端路由表、双向 Ping 都按采集材料格式提交，四项目标从 0/4 恢复到 4/4。华为 VRP 格式样例也保留公用表与按协议筛选的区分。这里的运行结果来自既有隔离 FRRouting 实采，MCP 联调使用这些记录回放；没有连到真实 eNSP、GNS3 或 EVE-NG。

### 保存并核验原始输出

可在本校 ICT 学院的数通机房使用已授权的 eNSP 环境或两台隔离的华为实验路由器。华为 eNSP Pro 官方下载和在线预约面向有相应权限的合作伙伴，学校教学实训的可用环境以校方安排为准。复现 `lab_02` 时，在修改前后都保留 `display version` 的型号和软件版本，以及两端 `display ospf interface` 的互联口区域与接口地址，便于核对区域是由接口配置还是进程下的 `network` 规则指定。[华为 eNSP Pro 说明](https://info.support.huawei.com/info-finder/encyclopedia/zh/detail?action=queryEntityDetail&keyword=eNSP+Pro) · [华为 OSPF 两端参数检查](https://info.support.huawei.com/network/ptmngsys/Web/tsrev_ce/cn/content/ce/12_edesk_dc_fail_to_establish_ospf_peer/edesk_dc_fail_to_establish_ospf_peer_edesk004.html)

没有实验环境时，先运行离线案例和评测即可；以下步骤用于后续设备验收。初始化只创建空目录，不生成命令输出：

```powershell
python -X utf8 scripts/verify_b_evidence.py init lab_02 runtime/b-evidence/lab_02
python -X utf8 scripts/verify_b_evidence.py check runtime/b-evidence/lab_02
```

在 `before/` 和 `after/` 各保存以下 UTF-8 原文：

| 文件 | 实际采集内容 |
| --- | --- |
| `R1-config.txt`、`R2-config.txt` | 两台路由器各自的 `display current-configuration` |
| `R1-ospf.txt`、`R2-ospf.txt` | `display ospf peer` 详情；无邻居时保留设备明确显示的零邻居汇总 |
| `R1-routes.txt`、`R2-routes.txt` | 两份完整的 `display ip routing-table` |
| `PC1-ping.txt`、`PC2-ping.txt` | 分别 Ping `192.168.20.10`、`192.168.10.10` 的原始收发统计 |

在 `record.json` 填写 `source`（`vrp_device` 或 `vrp_simulator`）、`environment`（型号和版本），以及两个阶段的 `captured_at`（带时区，如 `2026-11-12T14:00:00+08:00`）。确实完整采集路由表后，再把各阶段的 `complete_route_tables` 设为 `true`。

`lab_02` 也可以按设备整段保存，不用手工做 16 份文件。每阶段保留 `R1.txt`、`R2.txt`、`PC1.txt`、`PC2.txt` 各一份 UTF-8 终端原文，保存上表对应的命令行与全部输出。路由器的命令各执行一次；两台 PC 日志可各自使用 eNSP 的 `PC>` 提示符。若某命令试了多次，另存一份只保留本阶段对应命令及输出的副本供导入，原始日志照常留存。

```powershell
python -X utf8 scripts/verify_b_evidence.py import-terminals runtime/b-evidence/lab_02 before runtime/b-evidence/raw-before
python -X utf8 scripts/verify_b_evidence.py import-terminals runtime/b-evidence/lab_02 after runtime/b-evidence/raw-after
```

导入按命令拆分，只创建待核验文件，不修改原始终端文本、不填写采集来源或声明路由表完整。少命令、混入另一台设备或已有同名输出时，先处理提示；日志没有命令行时继续使用上表的手工保存方式。

重新运行 `check`。`verification.json` 给出缺失文件、配置匹配、邻居、两端远端 OSPF 路由及双向 Ping。`pending` 表示材料待补；`mismatch` 表示提交观测未符合本例预期；`recorded_observations_match` 表示记录与要求吻合。用测试夹具时必须选 `fixture`，结果仅为 `fixture_pass`。如设备输出格式不同，保留原文并记录差异，勿补写不存在的行。

设备或模拟器的路由表要保留公用表标记、目的地数、路由数及全部原始行。故障期「没有目标路由」须由可核验的完整公用表证明；修复期须有实际安装的目标 OSPF 路由。请把设备型号与软件版本、修改操作、截图/录屏和实验来源与原件一并保留。

通过核验的 `lab_02` 实采可导出同一会话用的材料。导出目录须使用新路径，不能位于原始采集目录内；缺材料、核验不通过或标为 `fixture` 时不导出。

```powershell
python -X utf8 scripts/verify_b_evidence.py export runtime/b-evidence/lab_02 runtime/b-evidence/lab_02-upload
```

人工确认权限、账号和设备信息后，先上传导出目录 `before/` 的 9 份材料，再在同一会话补充 `after/` 的同名材料并点「核对这一步」。两阶段各有同一份实验要求、两份配置、两份邻居、两份路由表和两份 Ping。导出会移除项目现有规则识别的敏感行，不含标准答案、核验报告或原始录屏。另在网页检查原文引用和下载报告，将同一轮材料留给课堂验收。
